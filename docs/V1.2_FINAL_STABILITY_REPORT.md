## Issue Resolution

### 1. Performance Optimization ✅

**Problem**: Assessment loading was serial (after Feishu load), adding ~200ms latency.

**Solution**:
- Start assessment load in parallel with Feishu load
- Added 2-second timeout protection for assessment queries
- Assessment store uses separate PostgreSQL database (no dependency on Feishu)

**Implementation**:
```javascript
// repository.mjs:1943-1944
const assessmentPromise = this.loadAssessmentSummariesSafe(customerId, 2000)
const database = await this.load()
// ... later
const assessmentResult = await assessmentPromise
```

**Impact**: Reduces latency by ~200ms when assessments are present.

### 2. Three-State Assessment Reading ✅

**Problem**: Assessment read failures returned `[]`, indistinguishable from "no assessments", causing incorrect fingerprint computation and unnecessary refreshes.

**Solution**:
- Return three-state object: `{ status: 'NONE' | 'OK' | 'FAILED', summaries: [], errorCode: '' }`
- When `FAILED`: don't change fingerprint, preserve stored understanding
- Prevents transient errors from triggering refresh cycles

**Implementation**:
```javascript
// assessment-understanding.mjs:158-180
export function createAssessmentResult(status, summaries, errorCode = '') {
  return { status, summaries, errorCode }
}

export function assessmentResultFingerprint(assessmentResult) {
  if (assessmentResult.status === 'FAILED') return ''
  // ... compute fingerprint only for OK/NONE
}
```

**Test Coverage**:
- `assessment-understanding-v12-final.test.mjs`: 13 tests
- `assessment-v12-final-integration.test.mjs`: 9 tests

### 3. Auto-Refresh Cost Control ✅

**Problem**: V4→V5 prompt upgrade triggered auto-refresh for all customers, burning through daily 100-call limit.

**Solution**:
- Introduce **base fingerprint** (excludes assessments) alongside **full fingerprint** (includes assessments)
- Dashboard uses base fingerprint for STALE detection
- Auto-refresh only triggers when base fingerprint changes (profile data changed)
- Assessment-only changes: status becomes STALE but no auto-refresh

**Implementation**:
```javascript
// customer-understanding.mjs:162-180
export function understandingBaseFingerprint({ customer, evidenceItems, conflicts }) {
  // Computes fingerprint WITHOUT assessments
}

export function understandingInputFingerprint({ customer, evidenceItems, conflicts, assessmentSummaries }) {
  const baseFp = understandingBaseFingerprint({ customer, evidenceItems, conflicts })
  // Adds assessment hash to base fingerprint
}

// App.tsx:1068-1080
const storedBaseFingerprint = response.meta.baseInputFingerprint || ''
const currentBaseFingerprint = response.meta.currentBaseFingerprint || ''
if (storedBaseFingerprint === currentBaseFingerprint) {
  return // Skip auto-refresh
}
```

**Impact**:
- V4→V5 upgrade: No auto-refresh (base fingerprint unchanged)
- Assessment import: No auto-refresh (base fingerprint unchanged)
- Profile update: Auto-refresh triggered (base fingerprint changed)

### 4. Data Protection ✅

**Problem**: Assessment read failures could cause incorrect analysis or display stale conclusions.

**Solution**:
- When assessment read fails: use stored understanding as-is
- Don't recompute fingerprint on failure
- Set `assessmentUnavailable: true` flag in response
- Prevents display of incorrect conclusions

**Implementation**:
```javascript
// repository.mjs:1087-1089
const effectiveFingerprint = assessmentUnavailable
  ? (storedMeta.inputFingerprint || fingerprint)
  : fingerprint

// repository.mjs:2047-2048
if (assessmentResult.status === 'FAILED') {
  return customerUnderstandingResponse({
    customerId,
    customerRecord,
    context: fallbackContext,
    storedMeta,
    assessmentUnavailable: true
  })
}
```

**User Experience**:
- If assessment read fails: user sees last successful analysis
- No incorrect conclusions displayed
- User can manually retry by refreshing the page

## Fingerprint Architecture

### Two-Layer Fingerprint System

```
┌─────────────────────────────────────────┐
│   Full Fingerprint (input_fingerprint)  │
│   = base + assessment_hash              │
│   Used for: refresh decisions           │
└─────────────────────────────────────────┘
                    │
                    │ includes
                    ▼
┌─────────────────────────────────────────┐
│   Base Fingerprint (base_input_fingerprint) │
│   = customer profile + evidence + context │
│   Used for: dashboard STALE, auto-refresh │
└─────────────────────────────────────────┘
```

### Behavior Matrix

| Scenario | Base FP Changed? | Full FP Changed? | Dashboard STALE? | Auto-Refresh? |
|----------|------------------|------------------|------------------|---------------|
| Profile update | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes |
| Assessment import | ❌ No | ✅ Yes | ❌ No* | ❌ No |
| Prompt upgrade (v4→v5) | ❌ No | ❌ No | ✅ Yes** | ❌ No |
| Assessment read failure | ❌ No | ❌ No | ❌ No | ❌ No |

*Dashboard doesn't load assessments, so it can't detect assessment changes. User must open customer detail to see STALE status.  
**Dashboard marks as STALE due to prompt version mismatch, but auto-refresh doesn't trigger (base FP unchanged).
